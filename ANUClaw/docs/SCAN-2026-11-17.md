# ANUClaw diagnostic scan — 17 November 2026

Broad source and local verification scan of the ANUClaw checkout. This is an
engineering assessment, not validation of clinical content or certification.
No application source fixes were made during this scan. Dashboard dependencies
were installed without lifecycle scripts or lockfile changes, and build outputs
were regenerated for verification.

## Verification results

| Check | Result |
|---|---|
| Backend `npm run build` | Passed |
| Full `npm test` | 37 files, 267 tests passed |
| Dashboard `npm run build` | Passed after installing its declared dependencies |
| `npm run lint` | Failed: ESLint 9 cannot find a flat configuration |
| Installed `pdf-parse` export inspection | Exports an object with `PDFParse`; is not callable |
| Direct configured PostgreSQL connection / `SELECT 1` | Connection refused; query could not run |
| Docker daemon | Unavailable at configured local socket |
| OCR / dashboard / API local HTTP checks | No response on ports 4001 / 3722 / 4000 |
| Default `python3` OCR dependencies | PaddleOCR, Paddle, FastAPI, Uvicorn not installed |
| Dashboard JWT secret / CDS auth environment | Not configured in this process after loading project configuration |

Not responding does not mean a service's implementation is broken. It means its
end-to-end behavior could not be verified here. No database migrations, patient
writes, messaging sends, or new medical-document uploads were performed. No live
model calls were made in this scan; the preceding model smoke test was separate.

## High-priority findings

### 1. PDF extraction calls the wrong library API — confirmed

[Upload parser](../src/dashboard/server/routes/elab.ts#L188) calls
`require('pdf-parse')(buffer)`. The installed v2 dependency is an object, not a
function. Its exported parser is `PDFParse`. The resulting exception is caught
and logged, then processing continues without the report text. The OCR fallback
is inside the same try block after the broken call, so it is skipped too.

Repair the v2 integration, make extraction failure visible, and test text PDFs,
scanned PDFs, mixed pages, and a malformed PDF.

### 2. Patient retrieval is not isolated by user, group, or tenant — confirmed source defect

[RAG patient search](../src/rag.ts#L19) queries the entire `patients` table by
common keywords. It receives `groupId` but only uses that to scope memory facts,
not patient records. [Every agent run](../src/container-runner.ts#L48) injects
retrieved records into the model context. This can mix unrelated patients into
answers and disclose records to unrelated agent sessions. Scope patient access
to an authorized patient and tenant before retrieval or model egress.

### 3. Authentication has unsafe defaults and missing-session acceptance — confirmed

[Dashboard auth](../src/dashboard/server/auth.ts#L6) uses a known fallback signing
secret when deployment secrets are absent; this scan found no configured secret.
It rejects a revoked session but accepts a missing session row. The
[refresh route](../src/dashboard/server/routes/users.ts#L140) does the same.
[Database initialization](../src/db/connection.ts#L316) seeds fixed administrator
credentials on a fresh database. [Password hashing](../src/dashboard/server/routes/users.ts#L8)
uses fast SHA-256 with a shared constant salt.

Require a configured signing secret, require an existing active session, remove
fixed production credentials, and use a password hashing function with per-user
salts. Existing accounts were not inspected or tested.

### 4. Clinical API authentication can be disabled by absent configuration — confirmed

[CDS router](../src/api/routes/cds.ts#L58) warns when auth is disabled but still
mounts clinical endpoints. [Guards](../src/api/middleware/cds-auth.ts#L68) then call
`next()` without authorization. No CDS auth key was configured in this scan.
The main API binds without a loopback host restriction. Fail closed outside an
explicit local demonstration mode. No remotely reachable deployment was tested.

### 5. Privacy handling differs between report routes — confirmed

Dedicated E-LAB assistive routes de-identify input before sending it to models.
The [upload/skill route](../src/dashboard/server/routes/elab.ts#L176) only adds an
optional instruction to redact output, then forwards extracted report content
to `runAgent`. Its audit metadata also stores a prompt excerpt and filenames.
The [host fallback](../src/container-runner.ts#L275) sends the prompt and retrieved
patient context directly to OpenRouter. Output masking does not remove input
identifiers before egress. Apply one consistent pre-egress policy to all paths.

### 6. Clinical rules are illustrative, and dashboard grants bypass real provisioning — confirmed

[Oncology](../src/cds/clinical/oncology/data.ts#L1),
[neurology](../src/cds/clinical/neurology/data.ts#L1), and
[PGx rules](../src/cds/data/cpic-rules.ts#L1) explicitly identify their content as
seed data requiring specialist validation; some citations are placeholders.
Passing deterministic tests establishes software behavior, not clinical validity.
Separately, [dashboard tenant creation](../src/dashboard/server/routes/elab-engine.ts#L54)
unconditionally grants clinical scope, active BAA status, and all enabled domains
to the authenticated dashboard user. The clinical endpoints require MFA but do
not restrict those grants to a clinical role. Replace demonstration grants and
validate rule content before clinical deployment.

## Functional defects and incomplete integration

### 7. OCR remains an unverified legacy integration

[OCR server](../ocr_server.py#L23) calls `ocr.ocr(..., cls=True)` and assumes the
legacy nested result format. It processes only `result[0]`, discards confidence
and layout, and returns an error object with HTTP 200. The
[upload heuristic](../src/dashboard/server/routes/elab.ts#L192) only invokes OCR
when whole-document text is under 50 characters, missing mixed scanned/text
pages. No OCR service was running, and the default Python environment lacks its
dependencies. Exact PaddleOCR compatibility still needs verification in the
intended pinned OCR environment. Gemini OCR has not been implemented.

### 8. Dashboard scheduling does not execute the configured tasks — confirmed

The [dashboard](../src/dashboard/server/routes/tasks.ts#L8) saves `scheduled_tasks`,
while the [scheduler](../src/task-scheduler.ts#L32) reads `tasks`. There is no bridge
between them. The [manual trigger](../src/dashboard/server/routes/tasks.ts#L119)
only inserts a log and updates status before reporting success; it never invokes
an agent. Also, the scheduler expects `task.groupId`, while PostgreSQL rows have
`group_id` and the database wrapper does not rename fields. Existing jobs are
skipped on reload, so changing a cron or prompt in place does not replace them.

### 9. Pipelines can report failed agent runs as completed — confirmed

[Pipeline execution](../src/dashboard/server/routes/pipelines.ts#L240) consumes
`result.text` without checking `result.error`. The agent runner normally returns
an error field rather than throwing. Consequently a failed node can be passed
downstream and the run marked completed. Connections are stored but execution
walks `pipeline.nodes` in array order, rather than using the connection graph.

### 10. EHR search route is shadowed, and writes do not establish persistence — confirmed

In [EHR routes](../src/api/routes/ehr.ts#L63), `/patients/:uid` is registered before
`/patients/search`; Express handles `search` as a UID. The later search handler
is therefore unreachable through its documented path. Registration calls
`runAgent` and returns HTTP 201 without validating `result.error` or a persisted
patient record. In text-only host fallback mode a generated response is not
proof that an EHR write occurred. Separate actual record operations from prose.

### 11. Container execution contract is incomplete — source finding, runtime unverified

The [runner](../src/container-runner.ts#L52) writes context to a mounted JSON file
and [sends credentials JSON to stdin](../src/container-runner.ts#L130). The
[image](../container/Dockerfile#L136) runs the stock Claude CLI without a bootstrap
that loads that file or exports the credentials payload. Media upload paths are
host paths and the upload directory is not among the mounted directories.
An isolated Docker smoke test is needed to establish actual CLI behavior.

The [host fallback](../src/container-runner.ts#L241) makes a text completion with
no tool-execution loop. It cannot perform scientific computation or EHR mutations
merely by describing them. Non-OpenRouter fallback returns an unsupported-provider
message without setting an error. Calls also lack HTTP timeouts, and a terminated
container can enter fallback before the runner handles its timeout result.

### 12. Hook controls are not consistently enforced — confirmed

[Message handling](../src/index.ts#L65) honors a BeforeLLMCall block but ignores
that hook's modified prompt. It uses AfterToolCall and AfterMessage payloads
without checking their `allowed` flags. [Hook exceptions](../src/hooks.ts#L77)
are logged and skipped. Uploads and pipelines call `runAgent` directly rather
than traversing this message-hook flow. A gate displayed in the UI does not
therefore guarantee enforcement across entry points or individual tool calls.

### 13. The new model review is limited to second opinion — confirmed scope gap

[Decision 1 → Gemma](../src/dashboard/server/routes/elab-engine.ts#L267) is used by
`/second-opinion` only. General skill runs, uploads, patient analysis, and pipelines
still use the [old verification loop](../src/container-runner.ts#L336), which uses
the primary model and returns the original output if review fails. It does not
automatically run scientific/clinical engines. The
[second-opinion UI](../dashboard/src/pages/ELab.tsx#L706) silently omits malformed
engine-verdict JSON rather than showing an error, potentially losing an intended
block. Engine evidence is caller-supplied, not verified server execution receipts.

### 14. Requested embeddings and general vital-sign rules are not implemented

[RAG](../src/rag.ts#L6) is keyword matching over patient rows, skill text, and memory
facts. It does not call Gemini Embedding 2 or maintain a vector index. No general
adult/pediatric vital-sign normalization and sourced threshold engine was found
in the scanned runtime. Existing vitals extraction is a model prompt, not that
rules engine. These are pending features rather than regressions.

### 15. Channel support is partly incomplete — confirmed examples

[Nostr sending](../src/channels/nostr/channel.ts#L54) only logs a stub message;
it does not sign or publish a reply. Feishu and DingTalk `start()` fetch tokens
but do not establish their advertised inbound stream connections; their
`handleWebhook` methods require separately wired ingress, which was not found
in the scanned servers. External channel accounts were not connected or tested.

### 16. Rate limits and quotas are deliberately bypassed — confirmed

[Rate/quota middleware](../src/api/middleware/rate-limit.ts#L4) is explicitly
pass-through. The application does not enforce those limits even though tenant
and usage fields exist. This is a current design choice with potential cost and
availability consequences, not an accidental compiler failure.

### 17. Linting is broken — reproduced

The package uses ESLint 9 and `npm run lint`, but has no applicable
`eslint.config.js`, `.mjs`, or `.cjs`. The command exits before checking source.
Supply a matching configuration and TypeScript parser setup.

## Recommended repair order

1. Enforce patient scoping, authentication defaults, clinical grants, and consistent
   pre-egress privacy handling.
2. Restore the local services and verify the container execution contract.
3. Repair PDF extraction and OCR with explicit extraction failure handling.
4. Repair task execution, pipeline failure propagation, and EHR routing/persistence.
5. Unify review coverage and enforce hooks across entry points.
6. Implement the requested embedding retrieval and sourced vital-sign engine.
7. Complete channel adapters and lint setup; validate clinical content separately.

The passing test suite is concentrated on CDS, engine logic, and a few helper
modules. It does not establish successful dashboard login, uploads, scheduling,
patient access isolation, live docking, or the complete report-to-SOAP workflow.
The 1100+ skill documents and their external tools were not individually executed.
