### Task 5 detail — passwords and sessions

- `src/security/password.ts`: async `crypto.scrypt`, 16-byte random salt per hash,
  format `scrypt$1$<log2N>$<r>$<p>$<salt>$<key>`, target N=2^15 r=8 p=1, stored
  parameters bounded (log2N 14–17, r 8–16, p 1–4), strict parser (malformed → reject,
  never throw), `timingSafeEqual`, dummy scrypt for unknown users / malformed rows,
  1024-char input cap. Legacy SHA-256 rows verify and return `needsRehash`.
- All password writers use scrypt: user create, password change, bootstrap.
  Minimum new-password length raised 8 → 12.
- Login: verify → if `needsRehash`, compare-and-set `UPDATE … WHERE password_hash = <verified>`
  → `issueTokens(expectedPasswordHash)`; a lost CAS or changed hash ⇒ 401, no session.
- `issueTokens` runs in a transaction taking `FOR SHARE` on the user row.
  `setPasswordAndRevokeSessions` updates the user row first, then revokes all sessions,
  in one transaction. Refresh **rotates**: old session revoked by CAS in the same
  transaction as the new one (one winner; reuse ⇒ 401). Logout revokes the access-token
  session and the refresh session (same user only).
- Bootstrap/migration concurrency: inspected — **no lock existed**. Added
  `pg_advisory_xact_lock` at the start of the migration transaction and inside
  `bootstrapFirstAdmin`.
- Users route 500s no longer return internal error messages; role values validated on update.

Evidence:
- mock: `src/security/password.test.ts` (18), `src/dashboard/server/login.test.ts` (7),
  updated `auth.test.ts` (rotation, reuse), `admin-bootstrap.test.ts` (lock before insert).
- real-PG (`src/db/pg-integration.test.ts`, 7 tests, all passed):
  - CONTROL: two transactions using only `INSERT … WHERE NOT EXISTS` both insert (2 rows) — the gap is real.
  - 6 concurrent migrations with bootstrap config ⇒ exactly 1 admin.
  - 6 concurrent `bootstrapFirstAdmin` transactions outside the migration ⇒ exactly 1 admin.
    With the bootstrap lock removed (mutation) this test fails (duplicate-key race), i.e. the lock is load-bearing.
  - Removing the lock from *both* places did **not** break the concurrent-migration test:
    the migration's `ALTER TABLE … ADD COLUMN IF NOT EXISTS` statements take exclusive
    locks that incidentally serialise whole migrations. The explicit lock is kept so
    correctness doesn't depend on that.
  - Login blocked behind an uncommitted password change ⇒ `password_changed`, 0 sessions.
  - Password change blocked behind an in-flight session insert ⇒ that session ends revoked.
  - 5 concurrent refreshes of one session ⇒ exactly 1 succeeds, 1 active session.
  - Legacy-upgrade CAS loses to a concurrent password change; the newer hash stays.
